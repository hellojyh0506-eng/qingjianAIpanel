## 三、根因分析：哪一层真正解决了问题？

为了严格区分各技术层级的实际贡献，避免“贪天之功于 LLM”，进行解耦归因：

### 1. Dictionary 层（词库基础）
- **贡献**：基础词条必须存在，否则任何解码器无米之炊。
- **实证证据**：本次测试中发现“再住一天”由于词库缺失最初匹配成“在注意天”。在词库补录 `再住一天` (5,000)、`住一天` (15,000)、`傻子吧` (8,000) 并重打包 `dict.qj`（92,829 条）后，整句直达率立即转为 100%。

### 2. Context & Scorer 层（规则驱动的对数几率修正）
- **贡献**：**这是实现 Top-1 颠覆性反转的核心引擎（主力层）**。
- **机制原理**：`disambiguation::contextual_score_adjustment` 在 Viterbi DP 边权重和单候选打分中直接注入 $\Delta \ln P$。
  - 例如 `的` (10,189,450) vs `得` (291,636)，基线词频差距为 $35:1$（对数差值约 $3.55$）。
  - 在动词“跑”后，注入 `得 (+4.5)` 与 `的 (-3.5)`，产生高达 $+8.0$ 的对数级优势（$e^{8.0} \approx 2980\times$），以绝对数学优势冲垮基线静态词频，将“得”直接推向 Top-1。
- **延迟代价**：仅做字符串尾部切片与单字匹配，单次查询仅 **0.7 ~ 3.6 微秒**，对用户打字速度**零损伤**。

### 3. Local Model 层（本地 8 层 Transformer，`model.qjm`）
- **贡献**：负责非规则长句的二阶平滑重排（Rescoring）。在停顿 80ms 后介入，不会阻碍首键输出。

### 4. Cloud Model 层（Qwen/Qwen2.5-7B-Instruct via SiliconFlow）
- **贡献与边界明晰**：
  - **Qwen 并没有、也不应该参与即时拼音选字**！如果把按键交给 7B 模型，打字将产生 500ms 灾难级延迟。
  - **Qwen 的真实职责**：仅在 Level 3 承担**整句长尾预测补全（☁ 联想）**与**被动英文翻译（Passive Translation）**。
  - **实机实测延迟**：在 `real_host_passive_translation_empirical` 中实测为 **506 ms** 和 **551 ms**，完全在后台线程异步执行，主候选窗口在 1ms 内正常呈现中文并支持直接空格上屏。
