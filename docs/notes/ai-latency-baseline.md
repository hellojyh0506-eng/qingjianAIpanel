# AI 打字识别延迟基线（P1）

2026-10-13。记录 P1（关思考、拆分模型、连接预热、`--ai-bench`）落地时的状态，后续阶段在同一份样本上对比。

## 做了什么

- `ThinkingSwitch` 新增 `EnableThinkingFlag`：SiliconFlow、阿里百炼发 `enable_thinking: false`。原来只有智谱会关，Qwen3 在这两家默认先思考，
  `max_tokens = 96` 的纠错请求被思考吃光，正文为空。
- 打字类请求强制关思考，温度 0 / 0.3；`StreamChatClient` 默认关思考。
- `typing_model` / `panel_model` 分开配置，Windows Server 里学习助手与 AI 问答改读 `panel_model`。
- 连接预热：Worker 启动与空闲 45 秒后的首个请求触发，连接池空闲超时 300 秒。

## P3 前后的本地对比

P3（`feat(correction)`）补了 `multi` 类样本（`gen_multi_samples.py`：100 句日常句，每句 2–3 处隔开的敲错，不碰末两位字母），并加了 `--local-bench` 只测本地。release 构建，同一份 `typing_samples.tsv`：

| 类别 | 条数 | P3 前 Top1 / Top3 | P3 后 Top1 / Top3 | 首选字符相似度 前 → 后 | P3 后首选标「纠」 | P3 后查询 P50 / P95 |
|---|---|---|---|---|---|---|
| typo | 120 | 64.2% / 66.7% | 65.8% / 68.3% | 82.5% → 83.1% | 79.2% | 1 / 8 ms |
| multi | 101 | 1.0% / 1.0% | 14.9% / 14.9% | 63.5% → 78.1% | 86.1% | 10 / 21 ms |
| clean | 300 | 97.0% / 99.3% | 97.0% / 99.3% | 97.9% → 97.9% | 0.3%（1 / 300，`ximina` → 西面） | 0 / 1 ms |
| context | 60 | 40.0% / 88.3% | 40.0% / 88.3% | 不变 | 0% | 0 / 0 ms |

- 验收「本地 Top1 ≥ 55%（120 条 typo）」：65.8%，满足（P1 时就已 64.2%，这份样本里单处错误占多数，分不出 P3 的收益，所以才补了 multi）。
- 验收「clean 误纠 ≤ 1%」：首选被标「纠」的是 0.3%；clean Top1 与 P3 前完全一样。
- multi 整句精确命中仍只有 14.9%：多数样本里被敲错的音节本身是合法音节（`fafeiwo`），只靠本地词图和语言模型分不清，要靠 P4 的 AI Resolve；
  但首选与期望的字符相似度从 63.5% 升到 78.1%，说明多数句子已经只差一两个字。
- 查询耗时：≤ 12 位的输入 P95 ≤ 8 ms；P3 前 20+ 位的长串每键 ~700 ms（两处编辑穷举），现在 `--typing zhegewentiwoijingiejueele` 平均 3.6 ms、最慢 6.9 ms。
  计划的「本地候选 P95 ≤ 3 ms」只在 clean / context 与短 typo 上成立（P95 0–1 ms），20+ 位的长串仍在 5–25 ms，是原来整句转换的开销（不是这次新增的），没有达标，如实记录。

## P4（Resolve）后的云端小样本试测

沙箱有了临时密钥后做了一次 SiliconFlow 小样本试测（`--bench-limit 10 --rounds 1`，每类 10 条共 40 条，两个模型各一轮）。**沙箱到 SiliconFlow 的单次往返约 0.5 s（TCP 0.53 s + TLS 1.0 s），比用户网络慢得多，这里的 P50 / P95 不能当作用户体验，「P50 ≤ 700 ms」在沙箱里无法验证**；小样本也只有 10 条，数字只能看趋势。

| 模型 | 类别 | 发请求 | 本地 Top1 | +AI Top1 | +AI Top3 | P50 / P95 | 无有效建议 | 首位标「纠」 |
|---|---|---|---|---|---|---|---|---|
| Qwen3-8B | clean | 0 | 100% | 100% | 100% | - | - | 0% |
| Qwen3-8B | context | 10 | 30% | 60% | 80% | 1204 / 1379 ms | 0% | 80% |
| Qwen3-8B | typo | 9 | 90% | 90% | 90% | 1449 / 2155 ms | 0% | 90% |
| Qwen3-8B | multi | 9 | 10% | 10% | 10% | 1633 / 2626 ms | 55.6% | 100% |
| Qwen3-14B | clean | 0 | 100% | 100% | 100% | - | - | 0% |
| Qwen3-14B | context | 10 | 30% | 60% | 80% | 999 / 1265 ms | 0% | 30% |
| Qwen3-14B | typo | 9 | 90% | 90% | 90% | 1097 / 1824 ms | 22.2% | 90% |
| Qwen3-14B | multi | 9 | 10% | 10% | 10% | 1211 / 1434 ms | 44.4% | 100% |

误纠率两个模型都是 0 / 10（clean 没有上下文、本地读音恰好等于键入串，Core 判为「本地把握大」不发请求）。

- **typo**：+AI 与本地持平。这批 typo 本地已有纠正候选，模型多半只是把它选回来，没有额外收益。
- **context**：Top1 由 30% 升到 60%，但没到 85%。样本全是单音节（`ta` 他 / 她 / 它、`de` 的 / 地 / 得），两个模型都会在「小猫 → 它」「小王 → 他」这类上选错；8B 与 14B 在这 10 条上没有区别。
- **multi**（多处错拼的整句）：基本没有改善。模型回的拼音常常自己也拼错（例如 `zuijingongzutetiemang`），被 Core 的编辑距离 / 完整切分校验拒掉，所以「无有效建议」高达 44–56%；选中的候选文字也常常是本地候选里的错句。这是模型能力问题，不是校验太严；8B / 14B 都不行，P6 选型时需要换更强的模型再测。
- 因此 P4 的验收（本地 + AI Top1 ≥ 80%、context Top1 ≥ 85%）**没有达到**，如实记录；校验与放置逻辑（误纠 0%、不会把坏结果顶到第 1 位）是可靠的，缺的是模型质量，留给 P6。
